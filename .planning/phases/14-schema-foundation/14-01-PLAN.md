## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Tampering | `Card.kartexId` (D-03 — no character restriction) | accept | Per D-03, `kartexId` accepts any non-empty string. Risk surface is internal (parsed from owner-uploaded .kartex files in Phase 16) and used only as a composite-unique scalar for diffing. No SQL injection risk because Prisma parameterizes; no XSS risk because the value is never rendered as HTML. ASVS L1 not violated. |
| T-14-02 | Information Disclosure | `ReviewLog.userId + reviewedAt` index | mitigate | Per D-08, the compound index forces every stats query to scope by `userId` to hit the index. Plan 03's rate endpoint always sets `userId` from the JWT context (never from request body). Phase 15 stats queries must include `where: { userId }` — enforced by code review in Phase 15. |
| T-14-03 | Denial of Service | `ReviewLog` row growth | accept | Append-only table grows linearly with rating volume (small private-user app, 2–5 users). No retention policy required at this scale; Postgres handles billions of rows. Re-evaluate if user count ever exceeds 100. |
| T-14-04 | Repudiation | Rating events without audit trail | mitigate (resolves in Plan 03) | Currently `cardProgress.upsert` overwrites prior state with no history. Plan 03 closes this gap by writing one ReviewLog row per rating inside the same transaction (D-10). |
</threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → POST /api/study/rate | Authenticated user submits JSON `{ cardId, rating }`. Existing T-4-01 (ownership), T-4-02 (RateCardSchema validation), T-4-03 (server-side SM-2) gates apply unchanged. New ReviewLog write inherits those guarantees because it runs after the ownership check inside the same handler. |
| Application → DB (transaction) | New trust point: the ReviewLog write must not introduce a path where `deckId` is sourced from request body. Mitigation enforced by source-grep gate in acceptance criteria. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-08 | Tampering | `ReviewLog.deckId` could be falsified if sourced from request body | mitigate | D-11 mandates `deckId: card.deckId` (the variable already loaded for the ownership check). Enforced by source-grep gate in Task 2 acceptance criteria: positive gate matches `deckId: card.deckId`, negative gate ensures no `deckId: body.data` or `deckId: c.req` pattern exists. |
| T-14-09 | Repudiation | Rating without audit trail | mitigate | This plan adds the audit trail. Every successful rate call writes one ReviewLog row inside the same atomic transaction as the CardProgress upsert. Failure of either rolls back both — no orphan rows, no missing audit entries on successful state changes. |
| T-14-10 | Tampering | `ReviewLog.userId` could be falsified | mitigate | `userId` is sourced from `c.get('userId')`, which is set by the JWT middleware (existing pattern in all routes). Never from request body. Pre-existing T-4-01 mitigation extended to the new write. |
| T-14-11 | Tampering | `ReviewLog.rating` could be out of spec (e.g. 99) | mitigate | `rating` is the validated `body.data.rating` after `RateCardSchema.safeParse(...)`. Schema is `z.literal(1) \| z.literal(2) \| z.literal(3) \| z.literal(4)` — out-of-range values rejected at parse time before the handler proceeds. |
| T-14-12 | Denial of Service | Migration on populated production DB | mitigate | D-17: the migration only adds a new table and a new nullable column (no DEFAULT, no backfill). All DDL is metadata-only on Postgres for new-column/new-table operations; no table-rewrite or long-running lock. Migration safety preserved. |
| T-14-13 | Tampering | npm/pip/cargo installs | accept | This plan installs no new packages — only invokes existing `npx prisma` commands already in dev dependencies. Package legitimacy gate not triggered. |
</threat_model>

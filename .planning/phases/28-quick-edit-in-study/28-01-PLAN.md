<objective>
Compute and expose a server-trusted `canEdit` boolean on every study-session card so the frontend can gate the quick-edit menu (SEDIT-01, SEDIT-04). Adds the field to the shared Zod schema and computes it in both study endpoints, reusing already-fetched DeckShare data (zero new queries).

Purpose: `canEdit` is the single source of truth for whether the current user may edit a card's deck. It must be server-computed and trustworthy — the frontend cannot derive it (DueCard carries no ownerId/share data), and it must match the exact owner/EDIT-or-MANAGE semantics the PATCH route already enforces.

Output: `DueCardSchema.canEdit`, `canEdit` in `GET /api/study/due` and `GET /api/study/deck/:deckId` responses, and it.todo behavior documentation for the permission truth table.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-01 | Elevation of Privilege | canEdit computation in study.ts | medium | mitigate | `canEdit` is derived server-side from `deck.ownerId` and the user's own DeckShare rows only — never read from the request. It is a display hint; the authoritative gate is the independent `getDeckAccess` re-derivation in the card PATCH route (unchanged). |
| T-28-02 | Information Disclosure | canEdit on inactive share (/deck/:deckId) | low | mitigate | Explicitly AND the EDIT/MANAGE check with `share.isActive === true` so a deactivated share never yields `canEdit=true` (Pitfall 5). Residual (stale in-tab flag) is UX-only and 403s on save. |
| T-28-03 | Tampering | request-supplied canEdit | low | accept | The endpoints never read `canEdit` from input; a client sending it has no effect. No handling needed beyond not trusting input (already the case). |

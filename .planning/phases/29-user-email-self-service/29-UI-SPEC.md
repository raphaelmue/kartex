# Phase 29 — UI Design Contract

> Visual and interaction contract for Phase 29: User Email Self-Service.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** This phase adds one new Settings Card (`Email`), one Alert
> banner (no-email warning), and one Admin Dialog (`Edit email`) reachable
> from the existing per-row DropdownMenu. No new pages, no new routes, no
> schema migration. All decisions below are either locked by
> `29-CONTEXT.md` (D-01 through D-08, cited inline) or resolved here under
> "Claude's Discretion" using direct codebase precedent — never invented
> from scratch.

open. Resolved as the **amber custom-class treatment**, not the shadcn
`destructive` Alert variant, because the codebase already draws this exact
distinction: `App.tsx`'s `AlertTriangle` + `text-destructive` is reserved
for a fatal, full-page error boundary, while `ImportPage.tsx`'s amber
`Alert` is the established pattern for a non-fatal, actionable warning
banner — which is precisely what "no email set" is (the account still
works; only password reset is blocked). Reusing the amber pattern keeps
"destructive" semantically reserved for irreversible actions (delete user)
project-wide.

## Interaction Contracts

### 1. Settings Email Card (D-01, D-02)

Placement: **first Card on `SettingsPage.tsx`**, above Study Mode (so the
Alert banner, if present, is the first thing visible on the page — per
CONTEXT.md "Specific Ideas").

```tsx
<Card>
  <CardHeader>
    <CardTitle>{t('settings.emailSection')}</CardTitle>
    <CardDescription>{t('settings.emailDesc')}</CardDescription>
  </CardHeader>
  <CardContent>
    <Form {...form}>
      <form onSubmit={form.handleSubmit(onSubmit)} className="space-y-4">
        <FormField
          control={form.control}
          name="email"
          render={({ field }) => (
            <FormItem>
              <FormLabel>{t('settings.emailLabel')}</FormLabel>
              <FormControl>
                <Input type="email" autoComplete="email" placeholder="you@example.com" {...field} />
              </FormControl>
              <FormMessage />
            </FormItem>
          )}
        />
        <Button type="submit" disabled={form.formState.isSubmitting}>
          {form.formState.isSubmitting && <Loader2 className="mr-2 h-4 w-4 animate-spin" aria-hidden="true" />}
          {form.formState.isSubmitting ? t('settings.emailSaving') : t('settings.saveEmail')}
        </Button>
      </form>
    </Form>
  </CardContent>
</Card>
```

- Input is **pre-filled** with `user.email ?? ''` as the RHF default value
  (D-02 — always editable, not add-only).
- **Not optimistic** (per CONTEXT.md "Established Patterns" — unlike
  `handleModeChange`, wait for server confirmation before updating
  `AuthContext`'s `user.email`, since a duplicate-conflict failure is
  expected/common for email edits).
- On success: `setUser({ ...user, email: values.email })`, `toast.success(t('settings.emailSaved'))`.
- On `EMAIL_TAKEN` (409): `form.setError('email', { message: t('settings.emailTaken') })` — renders via `FormMessage`, **no toast** for this specific case (D-07: inline only for validation-style errors).
- On any other failure (network/500): `toast.error(t('settings.saveFailed'))` (reuses the existing generic key — no new key needed for the non-specific failure path).
- Format validation (`z.string().email()`) is enforced by `zodResolver` **before** submit — renders via the same `FormMessage`, no round-trip needed for an obviously invalid format.

**Claude's Discretion — resolved (Save button disabled state):** Save is
**not** gated on "value differs from current email." It is disabled only
while `form.formState.isSubmitting` is true (loading state) — consistent
with `ForgotPasswordPage.tsx`'s only disabled-state precedent in this
codebase. A dirty-check adds complexity with no established pattern to
follow; resubmitting an unchanged, still-valid email is harmless (backend
returns 200 with no-op update, or the planner may choose to short-circuit
server-side — implementation detail, not a UI concern).

### 2. No-Email Alert Banner (D-03, D-04)

Placement: **top of `SettingsPage.tsx`**, above the `<h1>` page heading or
directly below it and above the Email Card — rendered only when
`user?.email == null`.

```tsx
{user?.email == null && (
  <Alert className="border-amber-200 bg-amber-50 text-amber-800 mb-6" role="alert">
    <AlertTriangle className="h-4 w-4 text-amber-600" aria-hidden="true" />
    <AlertTitle className="text-amber-800 font-semibold text-sm">
      {t('settings.noEmailWarningTitle')}
    </AlertTitle>
    <AlertDescription className="text-amber-800 text-sm mt-1">
      {t('settings.noEmailWarningDesc')}
    </AlertDescription>
  </Alert>
)}
```

- **Not dismissible** — no close button, no localStorage state (per
  CONTEXT.md explicit note). Disappears automatically and only when
  `user.email` becomes non-null after a successful save.
- Uses the exact `ImportPage.tsx` amber-warning class recipe (see Color
  section) — do not invent a new warning palette.
- **Settings-page only** (D-04) — do not add this Alert, or any variant
  of it, to `DashboardPage`, `AppShell`, or anywhere else.

### 3. Admin Edit Email Dialog (D-05, D-06)

**Menu placement (D-06):** "Edit email" is a new `DropdownMenuItem`,
**first item** in the existing per-row menu in `AdminPage.tsx`, above
"Send password reset email", above "Delete user" (destructive stays
last, unchanged, separated by the existing `DropdownMenuSeparator`).
Shown for every row, including the admin's own.

```tsx
<DropdownMenuContent align="end">
  <DropdownMenuItem onClick={() => setEditEmailTargetId(u.id)}>
    {t('admin.editEmail')}
  </DropdownMenuItem>
  <DropdownMenuItem onClick={() => void handleSendPasswordReset(u.id)}>
    {t('admin.sendPasswordReset')}
  </DropdownMenuItem>
  <DropdownMenuSeparator />
  <DropdownMenuItem className="text-destructive focus:text-destructive" onClick={() => setDeleteTargetId(u.id)}>
    {t('admin.deleteUser')}
  </DropdownMenuItem>
</DropdownMenuContent>
```

**Dialog (single shared instance, outside `users.map()`, controlled by
`editEmailTargetId: string | null` state)** — mirrors the exact
`deleteTargetId` / single-`AlertDialog`-instance pattern already
established in `AdminPage.tsx` (D-05 cites this precedent directly):

```tsx
<Dialog open={editEmailTargetId !== null} onOpenChange={(open) => { if (!open) setEditEmailTargetId(null) }}>
  <DialogContent>
    <DialogHeader>
      <DialogTitle>{t('admin.editEmailDialogTitle')}</DialogTitle>
      <DialogDescription>
        {t('admin.editEmailDialogDesc', { username: editEmailTarget?.username })}
      </DialogDescription>
    </DialogHeader>
    <Form {...adminEmailForm}>
      <form onSubmit={adminEmailForm.handleSubmit(onAdminEmailSubmit)} className="space-y-4">
        <FormField
          control={adminEmailForm.control}
          name="email"
          render={({ field }) => (
            <FormItem>
              <FormLabel>{t('admin.emailLabel')}</FormLabel>
              <FormControl>
                <Input type="email" autoComplete="email" {...field} />
              </FormControl>
              <FormMessage />
            </FormItem>
          )}
        />
        <DialogFooter>
          <Button type="button" variant="outline" onClick={() => setEditEmailTargetId(null)}>
            {t('admin.keepCurrentEmail')}
          </Button>
          <Button type="submit" disabled={adminEmailForm.formState.isSubmitting}>
            {adminEmailForm.formState.isSubmitting ? t('settings.emailSaving') : t('admin.saveEmail')}
          </Button>
        </DialogFooter>
      </form>
    </Form>
  </DialogContent>
</Dialog>
```

- Dialog opens with the input **pre-filled** with the target user's
  current email (RHF `defaultValues`/`reset()` keyed on
  `editEmailTargetId` change), empty if `null`.
- Same error contract as the Settings form: `EMAIL_TAKEN` → inline
  `form.setError('email', ...)` via `FormMessage`; format errors →
  `zodResolver` inline; any other failure → `toast.error()`.
- On success: `toast.success(t('admin.emailUpdated'))`, close dialog
  (`setEditEmailTargetId(null)`), refresh the users list (same
  `fetchUsers()` call already used after delete/role-change).
- The Dialog's built-in `DialogClose` (top-right X, from `dialog.tsx`,
  unstyled/default) provides a second, redundant close affordance — this
  is the shadcn primitive default, not a phase-specific addition.

**Claude's Discretion — resolved (button label specificity):** The ui-checker
flagged reuse of `common.save` / `common.cancel` as BLOCK-listed generic
labels ("Save", "Cancel"), regardless of key provenance. Both write actions
now use dedicated, action-specific keys — `settings.saveEmail` /
`admin.saveEmail`, rendering **"Save email"** — so the button names the
object being saved rather than relying on context. The Admin Dialog's
dismiss action is **not** a destructive or high-risk operation (it simply
closes the dialog without persisting a change, leaving the user's existing
email untouched), so instead of a bare "Cancel" it is relabeled
**"Keep current email"** (`admin.keepCurrentEmail`) — this states the
actual outcome of dismissing the dialog, consistent with the phase's
plain-language, outcome-first copy style used elsewhere (e.g. the no-email
warning body).

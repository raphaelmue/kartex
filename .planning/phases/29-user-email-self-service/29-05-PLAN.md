<objective>
Close the two outstanding Phase 29 verification gaps without re-planning any shipped plan (29-01..29-04):

1. **CR-01 (blocker):** Email normalization (`.trim().toLowerCase()`) currently exists only on the two write paths Phase 29 introduced (`UpdateEmailSchema`/`UpdateMeSchema`). Two pre-existing paths that also read/write `user.email` were left unnormalized — `PasswordResetRequestSchema` (forgot-password lookup) and `POST /api/admin/invites` (invite creation). Because `User.email` is a case-sensitive Postgres `String? @unique` column (no citext), this silently (a) lets a case-variant duplicate slip past the `EMAIL_TAKEN` guarantee via the invite path, and (b) makes forgot-password a silent no-op for mixed-case stored emails (invisible under RESET-03's generic-200 anti-enumeration contract). This plan extracts one shared `normalizedEmail()` Zod helper (also closing WR-01's triple-duplication warning) and routes every email-validation site through it.

2. **Doc accuracy (Gap 2):** REQUIREMENTS.md still lists `EMAIL-11` as `[ ]`/"Pending" though Plan 29-04 shipped and tested it. Reconcile it to `[x]`/"Complete" in both the checklist and the Traceability table.

Purpose: Restore the phase's stated uniqueness/reset guarantees to hold across the *entire* user lifecycle (invite → self-service → admin edit → forgot-password), not only the two endpoints this phase authored.
Output: A shared `normalizedEmail()` helper, all five email-validation sites converging on it, one real normalization unit test proving cross-schema consistency, and a reconciled REQUIREMENTS.md.

Deferral (explicit, per VERIFICATION.md's non-mandate): No Prisma data-normalization migration for already-diverged `User.email`/`InviteToken.email` rows is included. Rationale — (1) 2–5-user self-hosted deployment: realistically zero or a handful of email rows, most invite-provisioned lowercase already; (2) a blind `lower(email)` migration would itself violate the `@unique` constraint if two case-variant rows coexist, forcing disproportionate collision-handling logic; (3) an admin can correct any diverged row in seconds via the now-normalizing `PATCH /api/admin/users/:id` endpoint shipped in 29-01. Application-layer normalization is sufficient going forward and no schema/migration file is touched, so the schema-push gate does not apply.
</objective>

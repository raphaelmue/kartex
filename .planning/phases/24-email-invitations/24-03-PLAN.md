  <action>
    Replace the `inviteCode` validation block with token-based registration. Destructure `{ username, password, token }` from the parsed body. First do an informational pre-check (not TOCTOU-safe, purely for user-facing error codes): `findUnique` the token and return 400 `{ error: 'NOT_FOUND' }`, 400 `{ error: 'ALREADY_USED' }`, or 400 `{ error: 'EXPIRED' }` for the three invalid states.

    Then perform consumption inside an interactive `prisma.$transaction(async (tx) => {...})`: (1) `tx.inviteToken.updateMany({ where: { token, usedAt: null }, data: { usedAt: new Date() } })` and if `result.count === 0` throw `new Error('TOKEN_CONSUMED')` — this is the atomic single-use guard that wins the concurrent-registration race (EMAIL-06); (2) check username uniqueness via `tx.user.findUnique` and throw `new Error('USERNAME_TAKEN')` if taken; (3) `tx.user.create` with `{ username, passwordHash: bcrypt.hash(password, 12), role: 'USER', email: invite.email }`. The role is always hard-coded `'USER'` — never accept a role from the client (privilege-escalation guard). Inside the transaction you MUST `throw` to abort, never `return` (Pitfall 7).

    Catch outside the transaction and map: `TOKEN_CONSUMED` → 400 `{ error: 'ALREADY_USED' }`, `USERNAME_TAKEN` → 409 `{ error: 'USERNAME_TAKEN' }`, otherwise rethrow. On success return 200 `{ message: 'Account created.' }`. The email comes from the consumed invite row, not from the request body — the invitee cannot register a different email (spoofing guard). Do not set auth cookies here (invitee logs in afterward).
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Unauthenticated client → /api/invites/:token | Public token-validation endpoint; attacker-controlled token value |
| Unauthenticated client → /api/auth/register | Public registration; attacker-controlled username/password/token |
| Authenticated admin → /api/admin/invites | Admin-gated invite creation/listing/revocation |
| Backend → SMTP server | Outbound invite email; admin-controlled recipient address |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-05 | Information Disclosure | Token guessability | high | mitigate | `randomBytes(32).toString('hex')` = 256-bit CSPRNG token; non-enumerable (Task 3); never cuid |
| T-24-06 | Spoofing | Single-use token replay | high | mitigate | Atomic `updateMany WHERE usedAt IS NULL` + count check in `$transaction` (Task 2); second use returns ALREADY_USED |
| T-24-07 | Tampering | TOCTOU race on consumption | high | mitigate | Interactive transaction makes mark-used + user-create atomic; concurrent callers cannot both win (Task 2) |
| T-24-08 | Spoofing | Expired token acceptance | medium | mitigate | `expiresAt < now` rejected in both pre-check (Task 2) and validate route (Task 1) |
| T-24-09 | Elevation of Privilege | Role injection at register | high | mitigate | `user.create` hard-codes `role: 'USER'`; no role read from request body (Task 2) |
| T-24-10 | Elevation of Privilege | Unauthorized invite management | high | mitigate | `/api/admin/*` is behind `requireAdmin` middleware (index.ts line 80); new invite routes inherit it |
| T-24-11 | Tampering | Email header injection | medium | mitigate | Recipient validated via Zod `.email()`; subject/body are fixed server constants — no user value in headers (Task 3) |
| T-24-12 | Spoofing | Invitee registers different email | medium | mitigate | `email` taken from consumed invite row, never request body (Task 2) |
| T-24-13 | Information Disclosure | Token value leakage via API | medium | mitigate | GET /invites and POST /invites `select` omit `token`; only id/email/dates returned (Task 3) |
| T-24-14 | Spoofing | Open registration without invite | high | mitigate | Register requires a valid unused non-expired token; no public path creates a user otherwise (Task 2) |
| T-24-SC | Tampering | npm installs | low | accept | No new packages; `node:crypto` is built-in, `nodemailer` already audited (RESEARCH Package Legitimacy Audit) |

# Phase 25 Plan 03: Backend Routes

## Goal

Implement the four server-side password reset routes: three public routes in auth.ts for the user-initiated flow, and one admin route in admin.ts for the admin-triggered flow.

## Artifacts this phase produces

- `POST /api/auth/forgot-password` — public; accepts email; always returns 200 (no enumeration); generates token, stores hash, sends email; rolls back token on email failure
- `GET /api/auth/reset-password/:token` — public; hashes raw token; validates PasswordResetToken (not expired, not used); returns ok or error code
- `POST /api/auth/reset-password/:token` — public; TOCTOU-safe atomic token consumption; updates User.passwordHash; deletes all RefreshToken rows; returns success
- `POST /api/admin/users/:id/reset-password` — admin (behind requireAdmin); checks user email present; generates token; sends email; returns NO_EMAIL / SMTP errors / success

<action>
In `apps/backend/src/routes/auth.ts`, make three changes:

Change 1 — Extend the import block:
- Add `import { randomBytes, createHash } from 'node:crypto'` (Node.js built-in — use named imports from 'node:crypto', not the Web Crypto global `crypto`)
- Add `PasswordResetRequestSchema, PasswordResetSchema` to the existing `@kartex/shared` import (alongside LoginSchema, RegisterSchema, UpdateStudyModeSchema)
- Add `import { sendMail, isConfigured } from '../lib/mailer.js'`

Change 2 — Append three new route handlers before the final `export { auth as authRouter }` line:

Route A — `auth.post('/forgot-password', ...)`:
1. Parse body with PasswordResetRequestSchema using safeParse. If invalid (not a valid email format), return 200 with a generic success message immediately — validation failures must not reveal user-enumeration information any more than an invalid email would.
2. Retrieve the user: `prisma.user.findUnique({ where: { email: body.data.email }, select: { id: true, email: true } })`.
3. If no user found or user.email is null: return 200 immediately with the same success-shaped response. This prevents email enumeration (RESET-03).
4. Guard APP_URL: if `process.env.APP_URL` is falsy, log the missing var with `console.error` and return 200 (do not leak server config state to the caller in the user-initiated flow).
5. Guard SMTP: if `!isConfigured()`, log and return 200 (same reasoning — user should not know SMTP is misconfigured).
6. Generate raw token: `randomBytes(32).toString('hex')` (64-char hex string).
7. Compute hash: `createHash('sha256').update(rawToken).digest('hex')`.
8. Set expiry: `new Date(Date.now() + 60 * 60 * 1000)` (1 hour — RESET-02).
9. Create PasswordResetToken row via `prisma.passwordResetToken.create({ data: { userId: user.id, tokenHash, expiresAt } })` — capture the returned row as `resetTokenRow` to use its `id` for rollback.
10. Compose reset link: `${process.env.APP_URL}/reset-password/${rawToken}`.
11. Send email inside a try/catch. Subject: 'Kartex — Password Reset'. Body text and HTML must include the reset link and state the link expires in 1 hour. Mirror the sendMail() call structure from admin.ts POST /invites (lines 203–209).
12. If sendMail() throws: delete the created PasswordResetToken row using `prisma.passwordResetToken.delete({ where: { id: resetTokenRow.id } })` wrapped in its own try/catch (same rollback pattern as admin.ts lines 211–217); log the delivery failure with console.error; return 200 (no enumeration — do not return an error to the user).
13. On success: return 200 with `{ message: 'If that email is registered, a reset link is on its way.' }`.

Route B — `auth.get('/reset-password/:token', ...)` (read-only validation for frontend mount check):
1. Extract raw token from `c.req.param()`.
2. Compute `tokenHash = createHash('sha256').update(token).digest('hex')`.
3. Query: `prisma.passwordResetToken.findUnique({ where: { tokenHash } })`.
4. If no record: return `{ error: 'NOT_FOUND' }` 400.
5. If record.usedAt is not null: return `{ error: 'ALREADY_USED' }` 400.
6. If record.expiresAt is less than `new Date()`: return `{ error: 'EXPIRED' }` 400.
7. Return `{ ok: true }` 200. Do NOT return user data — ResetPasswordPage does not need it (unlike InviteRegisterPage which returns email).

Route C — `auth.post('/reset-password/:token', ...)` (TOCTOU-safe consumption):
1. Extract raw token from `c.req.param()`.
2. Compute tokenHash as in Route B.
3. UX pre-check (not TOCTOU-safe — purely for informational error messages, per Pitfall 2 in RESEARCH.md): `prisma.passwordResetToken.findUnique({ where: { tokenHash } })`. If not found/used/expired, return matching 400 error code. Capture the record (carry `userId` into the transaction — Pitfall 3 in RESEARCH.md).
4. Parse request body with PasswordResetSchema using safeParse. If invalid: return 400 with validation details.
5. Execute `prisma.$transaction(async (tx) => { ... })` containing:
   a. Atomic single-use gate: `tx.passwordResetToken.updateMany({ where: { tokenHash, usedAt: null, expiresAt: { gt: new Date() } }, data: { usedAt: new Date() } })`. If `result.count === 0`, throw `new Error('TOKEN_CONSUMED')` to abort the transaction.
   b. Hash the new password: `await bcrypt.hash(body.data.newPassword, 12)`.
   c. Update user password: `tx.user.update({ where: { id: record.userId }, data: { passwordHash } })` — use `record.userId` from the pre-check (Step 3), not a nested query inside the transaction.
   d. Delete all refresh tokens: `tx.refreshToken.deleteMany({ where: { userId: record.userId } })` — invalidates all active sessions (RESET-05).
6. Catch TOKEN_CONSUMED: return `{ error: 'ALREADY_USED' }` 400.
7. On success: return `{ message: 'Password reset successfully.' }` 200. Do NOT issue a new JWT or set cookies — the frontend navigates to /login for re-authentication (D-01).

Note: The rate limiting middleware applied via `auth.use('*', rateLimitMiddleware(10, 60_000))` at line 14 automatically covers all three new routes — this is intentional and correct for security (Pitfall 1 in RESEARCH.md).
</action>

    AUDIT ITEM A — Comment stripping (§2):
    The doc states: "Any line whose first non-whitespace character is `#` is a comment... except `#typst`."
    Verify against parser regex: `/^\s*#(?!typst)/` — this matches lines where the first non-whitespace characters are `#` not followed by `typst`. Confirm this matches the doc's claim. Also verify the doc's statement: "They cannot appear inside a field value (a line like `front: # not a comment` treats the `#` as part of the value)." The parser's filteredLines condition also checks `!/^\s*(front|back|tags|deck|author)\s*:/.test(line)` — field assignment lines are never stripped even if they start with #. The doc's claim that `front: # not a comment` treats # as part of the value is accurate (because the line starts with `front:` which matches the guard pattern).

    AUDIT ITEM B — #typst block placement (§5.3):
    The doc states: "The line `#typst` must appear at the start of the field value (or on its own line within the value)."
    Verify against the parser: the parser does NOT have special logic to detect #typst blocks — it passes the raw field value (front/back content) through to the frontend renderer. The `#typst` string is preserved in field values because the comment-stripping regex only strips standalone lines, and `#typst` lines are explicitly excluded via the negative lookahead `(?!typst)`. The format doc accurately describes the rendering behavior, not parser behavior — this is correct because the parsing is transparent to field content.

    AUDIT ITEM C — Multi-line field values (§4):
    The doc states multi-line values continue "until the parser encounters another recognised field name (`front:`, `back:`, or `tags:`) or the closing `::`."
    Verify against parseFields(): the FIELD_PATTERN is `/^(front|back|tags):\s*(.*)/` — it matches exactly these three field names at the start of a line. The closing `::` is handled by the card block regex, not inside parseFields. This matches the doc's claim.

    AUDIT ITEM D — Tags as single-line field (§4):
    The doc's Tags Field section states tags is a "single-line field parsed as a YAML array."
    Verify against parseFields(): when the field name is `tags`, the parser sets `result.tags = fieldMatch[2].trim()` and sets `currentField = null` — no continuation lines are accumulated. This matches the doc's claim.

    AUDIT ITEM E — Block math $$ on own lines (§5.2):
    The doc states: "The `$$` delimiters must each appear on their own line" and has a note "A `$$` on the same line as content is treated as inline, not display mode."
    This is a rendering constraint (remark-math/rehypeKatex), not a parser constraint. The parser is content-transparent for field values. The doc correctly frames this as a rendering rule. No inaccuracy.

    AUDIT ITEM F — .kartex.zip bundle rules (§7):
    The doc states: "The archive must contain a file named `deck.kartex` at the root" and "All media files must live in the `media/` directory at the root."

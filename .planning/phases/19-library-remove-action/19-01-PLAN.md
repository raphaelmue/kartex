<objective>
Deliver LIB-02: a user can permanently remove a public/shared deck from their personal library.

The capability spans three changes:
1. Backend: a new `DELETE /api/decks/:id/library` route that deletes only the calling user's `DeckShare` row (preserving `CardProgress`), with an ownership check returning 403 when no share exists.
2. i18n: 5 new `decks.removeFromLibrary*` keys added atomically to both `en.json` and `de.json`.
3. Frontend: a ⋮ `DropdownMenu` on library deck cards (`ownerId !== user?.id` branch) with a single "Remove from library" item, a confirmation `AlertDialog`, a `removeTargetId` state variable, and a `handleRemoveFromLibrary` handler that calls the endpoint and optimistically removes the deck from the list.

Purpose: Closes the round-trip on the library lifecycle — Phase 18 added the active/inactive toggle; Phase 19 lets users fully remove a deck they previously added.
Output: One backend route + behavior-stub test, 10 new i18n entries (5 per locale), and the DecksPage UI wiring.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Hono API | Untrusted `id` route param and authenticated `userId` (from JWT cookie via authMiddleware) cross here |
| Hono API → PostgreSQL | Prisma compound-unique lookup/delete on DeckShare |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-01 | Elevation of Privilege / IDOR | DELETE /api/decks/:id/library | mitigate | Handler keys `deckShare.findUnique` on `{ deckId_sharedWithUserId: { deckId: id, sharedWithUserId: userId } }` where `userId = c.get('userId')` from JWT. A user cannot reference another user's share — the delete is always scoped to the caller's own `(deckId, userId)` pair. No `userId` ever comes from the request body or param. |
| T-19-02 | Spoofing / AuthZ bypass | DELETE /api/decks/:id/library | mitigate | Route sits behind the existing `authMiddleware` (same mount as PATCH /:id/library); `userId` is injected server-side. Unauthenticated requests are rejected before the handler runs. |
| T-19-03 | Information Disclosure | 403 vs 404 response for non-existent/non-owned shares | accept | Handler returns 403 ("Forbidden.") uniformly whether the DeckShare row is absent because it never existed or because it belongs to another user — this is the SAME behavior as the existing PATCH /:id/library route, so no new disclosure surface is introduced. A uniform 403 does not distinguish "deck exists but not yours" from "no share" beyond what PATCH already reveals. |
| T-19-04 | Tampering / Data loss | prisma.deckShare.delete scope | mitigate | Only `prisma.deckShare.delete` runs (D-09); no `CardProgress`, `Deck`, or `Card` mutation. The delete is keyed on the caller-scoped compound unique, so it cannot cascade to or affect other users' shares or the owner's deck (LIB-02 success criterion 4). Acceptance criterion greps for absence of `cardProgress` in the handler. |
| T-19-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed in this phase — all components (DropdownMenu, AlertDialog, Button, MoreVertical) and the Prisma client are already present. No package-legitimacy gate required. |

Residual risk: T-19-03 accepted — uniform 403 matches the established PATCH route behavior and reveals no more than the existing surface. No high-severity threats remain unmitigated; no blocking checkpoint required.
</threat_model>

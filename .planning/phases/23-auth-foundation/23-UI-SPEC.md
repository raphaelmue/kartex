## Interaction Contracts

### Delete User Flow (ADMIN-01, ADMIN-02, ADMIN-03, ADMIN-04)

1. Each user row in UsersSection has a 3-dot `DropdownMenuTrigger` (ellipsis icon, `variant="ghost"`, size `icon`).
2. The DropdownMenu contains a "Delete user" item styled with `className="text-destructive focus:text-destructive"` (established pattern from Phase 17).
3. A single `AlertDialog` instance lives **outside** the `users.map()` loop, controlled by `deleteTargetId: string | null` state (mirrors DeckDetailPage Phase 17 pattern — D-01).
4. AlertDialog body contains:
   - Static category list paragraph: "This will permanently delete their decks, cards, study progress, and review logs." (D-03)
   - A controlled `Input` where the admin types the target username (D-04)
   - The confirm `Button` (variant="destructive") is disabled until `inputValue === targetUsername`
5. On confirm: call `DELETE /api/admin/users/:id`. On success: `toast.success()`, refresh user list, close dialog. On 400 (self-delete or last admin): `toast.error()` with the error message from the server (D-08).

### Email Column Display (ADMIN-05)

- Add "Email" as a new `<TableHead>` column between "Joined" and "Actions".
- Cell displays `u.email` or `—` (em dash, `—`) for null emails (D-13).
- Display-only — no inline edit affordance in Phase 23 (D-14).

### Mailer Test Email Button (EMAIL-02, D-11)

- A new `MailerSection` card rendered above `InviteCodesSection` in `AdminPage`.
- Contains a single "Send test email" `Button` (variant="outline").
- On click: `POST /api/admin/mailer/test`. On success: `toast.success(t('admin.testEmailSuccess'))`. On error (no email set): `toast.error(t('admin.testEmailNoEmail'))`. On other error: `toast.error(t('common.somethingWrong'))`.
- Button shows loading state during request (disabled + spinner or loading label).

## Phase-Specific Notes

1. **No new pages** — all changes are additions to existing `AdminPage.tsx` and `apps/backend/src/routes/admin.ts`. No routing changes.
2. **No new CSS tokens** — existing `--destructive`, `--muted-foreground`, `--primary` tokens cover all new elements.
3. **AlertDialog placement** — single instance outside the `users.map()` loop, same DOM position as the existing inline confirm pattern in `InviteCodesSection`.
4. **MailerSection ordering** — rendered first in `AdminPage` body (above `InviteCodesSection`), consistent with infrastructure-first ordering.
5. **Dark mode** — inherited automatically via existing CSS variable system; no dark-mode-specific overrides needed.
6. **`e.stopPropagation()`** on the DropdownMenuTrigger inside the table row — prevents any parent row click handlers from firing (established pattern from v1.4-research decision).
7. **Focal point declaration** — The users table (UsersSection card) is the primary visual focal point of AdminPage. The MailerSection card is a secondary infrastructure utility; it is placed above UsersSection for discoverability but is visually subordinate (smaller footprint — single-button card vs. full data table).

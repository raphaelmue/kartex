  <decision>The schema migration must run against the database. Choose the migration command based on whether DATABASE_URL is available and whether a shadow DB is reachable.</decision>
  <context>
    This is the BLOCKING schema-push gate. Prisma Client type generation alone makes TypeScript pass even without applying SQL, producing a false-positive — DECK-02's isActive filter cannot actually exclude rows unless the column exists in the live DB. The executor must apply the migration before any backend/frontend feature work in Wave 2.

    Primary command (DATABASE_URL set, shadow DB reachable): `DATABASE_URL=... npx prisma migrate dev --name add_isactive_studymode --schema apps/backend/prisma/schema.prisma`. This generates the `ALTER TABLE "Deck" ADD COLUMN "isActive" BOOLEAN NOT NULL DEFAULT true;` (+ studyMode) migration, applies it, and regenerates Prisma Client. Both columns have `@default`, so existing rows are backfilled — zero downtime.

    Fallback (no shadow DB / non-interactive env): `DATABASE_URL=... npx prisma db push --schema apps/backend/prisma/schema.prisma` to sync the columns, then `npx prisma generate` to refresh the client.

    After applying, the executor MUST confirm the columns exist (e.g. `npx prisma migrate status` shows up-to-date, or a `\d "Deck"` / introspection shows isActive). Run `npx prisma generate` so Prisma Client carries `isActive` and `studyMode`.
  </context>
  <options>
    <option id="migrate-dev">
      <name>prisma migrate dev (preferred)</name>
      <pros>Creates a checked-in migration file, preserves migration history, regenerates client</pros>
      <cons>Requires DATABASE_URL and a reachable shadow database</cons>

    <option id="db-push">

      <pros>Works without a shadow DB; syncs columns directly</pros>

    </option>

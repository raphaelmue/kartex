## Layout & Structure

### Auth Pages (`/login`, `/register`) — No Sidebar

```
┌─────────────────────────────────────────────────┐
│                                                 │
│              (vertical center)                  │
│                                                 │
│         ┌─────────────────────────┐             │
│         │  [App Logo / Name]      │  Card       │
│         │  ─────────────────────  │  w=400px    │
│         │  [form fields]          │  max-w-full │
│         │  [CTA button]           │             │
│         │  [secondary link]       │             │
│         └─────────────────────────┘             │
│                                                 │
└─────────────────────────────────────────────────┘
```

- Page background: `bg-background` (neutral-50 in light)
- Card is horizontally and vertically centered using `min-h-screen flex items-center justify-center`
- Card width: `w-[400px]` with `max-w-[calc(100vw-32px)]` for narrow screens (no breakpoints — card shrinks on mobile)
- Card padding: 32px (xl) all sides
- Form field vertical gap: 24px (lg) between labeled field groups
- Button sits 32px (xl) below the last field
- Secondary link (e.g., "Don't have an account? Register") sits 16px (md) below the CTA button
- Page title (h1, sr-only) identifies the page for screen readers; visible heading inside card is the form title

Nav item anatomy:
- Height: 44px (touch target minimum — see Spacing exceptions)
- Padding: 8px (sm) vertical, 16px (md) horizontal

- Label: 14px, weight 400, same color rules as icon
- Active state: `bg-accent` background, icon and label switch to `text-accent-foreground`
- Hover state: `bg-accent/50` background
- Spacing between icon and label: 8px (sm)

## Spacing Scale

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps within components, badge padding |
| sm | 8px | Between nav icon and label, compact input internal padding |
| md | 16px | Default field spacing, card padding unit, horizontal nav padding |
| lg | 24px | Between form field groups (label + input pairs) |
| xl | 32px | Card padding, main content area padding, button-from-field gap |
| 2xl | 48px | Major section separators on admin page |
| 3xl | 64px | Sidebar brand area height, sidebar user area height |

Exceptions:
- Nav item height: 44px (WCAG 2.5.5 minimum touch target, not a multiple of 4 — accepted accessibility exception)
- Card `max-w`: `calc(100vw - 32px)` on small screens to ensure 16px gutters each side

## Color

shadcn/ui neutral theme. CSS variables are defined in `apps/frontend/src/index.css` by `npx shadcn init`. The values below are the semantic roles — do not hardcode hex values; use CSS variable tokens.

| Role | Token | Light Value (approx) | Dark Value (approx) | Usage |
|------|-------|----------------------|---------------------|-------|
| Dominant (60%) | `--background` | neutral-50 (#fafafa) | neutral-950 (#0a0a0a) | Page background, main content area |
| Secondary (30%) | `--card` | white (#ffffff) | neutral-900 (#171717) | Sidebar bg, auth card bg, table bg, admin section cards |
| Accent (10%) | `--primary` | neutral-900 (#171717) | neutral-50 (#fafafa) | CTA button fill, active nav item indicator |
| Destructive | `--destructive` | red-500 (#ef4444) | red-900 (#7f1d1d) | Delete invite code button, deactivate user button, form error messages |

Accent reserved for (explicit list):
1. Primary CTA button fill (Sign in, Create account, Generate code, Save changes)
2. Active nav item background highlight
3. Focus ring on all interactive elements

The `--muted` and `--muted-foreground` tokens handle secondary text (placeholder text, helper text, nav labels in inactive state). Use these — do not use opacity hacks.

Dark mode: shadcn/ui CSS variables flip automatically. No additional dark mode work required in Phase 1. The `class` strategy is used (`darkMode: 'class'` in tailwind.config.ts). No dark mode toggle in Phase 1 — it is inherited from OS preference via `prefers-color-scheme` at a later phase.

## Component Inventory

### Button

| Variant | Usage | Props |
|---------|-------|-------|
| `default` (filled) | Login CTA, Register CTA, Generate invite code, Save role change | `size="default"`, full-width on auth forms (`w-full`) |
| `destructive` | Delete invite code, Deactivate user | `size="sm"` inside table row |
| `outline` | Cancel in confirmation dialogs (if any) | `size="sm"` |
| `ghost` | Log out button in sidebar user area | `size="sm"` |

Button loading state: set `disabled` and render `<Loader2 className="mr-2 h-4 w-4 animate-spin" />` before the label text. No separate loading spinner component.

### Input

All inputs: `type` set explicitly (text, password). Never use `type="email"` for the username field — usernames are not emails.

| Field | Type | Autocomplete | Placeholder |
|-------|------|--------------|-------------|
| Username (login) | text | `username` | "Username" |
| Password (login) | password | `current-password` | "Password" |
| Username (register) | text | `username` | "Username" |
| Password (register) | password | `new-password` | "Password" |
| Invite code (register) | text | `off` | "Invite code" |
| Expiry days (generate code) | number | `off` | "7" |

Use react-hook-form + `@hookform/resolvers/zod` connected to shared Zod schemas from `@kartex/shared`. Each field uses the `<FormField>`, `<FormItem>`, `<FormLabel>`, `<FormControl>`, `<FormMessage>` pattern from shadcn Form.

Field error messages appear beneath the input as `<FormMessage>` — 14px, `text-destructive`, no icon.

- `<CardHeader>`: contains the page heading (20px, weight 600) and optional subtitle (14px, muted)

- `<CardFooter>`: contains the secondary navigation link (e.g., "Already have an account? Sign in")

Admin page: section grouping uses `<Card>` with `<CardHeader>` + `<CardContent>` for each section (invite codes section, users section).

### Toast (Sonner)

Toasts appear bottom-right. Configuration in `<Toaster />` component placed in root layout.

| Event | Type | Message |
|-------|------|---------|
| Login success | (silent — just redirects) | No toast |
| Login failure | (shown as inline form error, not toast) | — |
| Register success | (silent — redirects to /login) | No toast |
| Register failure | (shown as inline form error) | — |
| Invite code generated | success | "Invite code generated" |
| Invite code deleted | success | "Invite code deleted" |
| User role changed | success | "Role updated" |
| User deactivated | success | "Account deactivated" |
| Network error (unexpected) | error | "Something went wrong. Please try again." |

Toast duration: 4000ms (4 seconds). No action buttons on toasts in Phase 1.

## Interaction Contracts

### Login Flow

```
User lands on /login
  │
  ├─ Already has valid session (cookie present + /api/auth/me returns 200)
  │    → Redirect to /dashboard immediately (no flash of login form)
  │
  └─ No session
       → Render login form
       │
       ├─ User submits form with empty fields
       │    → react-hook-form client validation fires before API call
       │    → Show inline errors: "Username is required", "Password is required"
       │    → No API call made
       │
       ├─ User submits form with valid-looking inputs
       │    → Submit button shows loading spinner, disabled
       │    → POST /api/auth/login
       │    ├─ 200 OK → Set cookies (handled by backend) → navigate to /dashboard
       │    └─ 4xx → Show inline error under password field: "Invalid username or password"
       │         → Submit button re-enables
       │
       └─ User clicks "Don't have an account? Register" → navigate to /register
```

### Register Flow

```
User lands on /register
  │
  ├─ Already has valid session → Redirect to /dashboard
  │
  └─ No session
       → Render register form
       │
       ├─ Client validation (on submit):
       │    Username: required, 3-20 chars, alphanumeric + underscore only
       │    Password: required, minimum 8 characters
       │    Invite code: required, non-empty
       │
       ├─ User submits with valid inputs
       │    → Submit button: loading spinner, disabled
       │    → POST /api/auth/register
       │    ├─ 200 OK → navigate to /login (with success toast: "Account created. Please sign in.")
       │    ├─ 400 (invalid invite code) → inline error under invite code field: "Invalid or expired invite code"
       │    ├─ 409 (username taken) → inline error under username field: "Username is already taken"
       │    └─ other 4xx/5xx → toast error: "Something went wrong. Please try again."
       │
       └─ User clicks "Already have an account? Sign in" → navigate to /login
```

### Logout

- Triggered by "Log out" button (ghost variant) in sidebar user area
- No confirmation dialog
- POST /api/auth/logout
- On response (200 or any): clear local auth state, navigate to /login
- If POST fails: still clear local state and navigate to /login (fail-open for UX)

### Token Refresh (Silent)

- Transparent to user — no UI interaction
- `apps/frontend/src/lib/api.ts` fetch wrapper:
  - On any 401 response: attempt POST /api/auth/refresh once
  - If refresh succeeds: retry original request
  - If refresh fails (401/403): clear auth state, navigate to /login with toast: "Your session has expired. Please sign in again."
  - Concurrent requests during refresh: queue them behind a single in-flight refresh promise (not multiple refresh calls)

### Admin: Generate Invite Code

```
Admin on /admin page
  │
  ├─ Sees "Generate Invite Code" section above the invite codes table
  │    Contains: Expiry field (number input, default 7, min 1, max 365, label "Expiry (days)")
  │              "Generate" button (primary)
  │
  ├─ Admin clicks Generate
  │    → Button: loading spinner, disabled
  │    → POST /api/admin/invite-codes { expiryDays: N }
  │    ├─ 200 OK → toast success "Invite code generated" → table refreshes to show new code
  │    └─ error → toast error "Something went wrong. Please try again."
  │
  └─ Generated code is visible in the table — admin copies it manually (no clipboard button in Phase 1)
```

### Admin: Delete Invite Code

```
Admin clicks "Delete" in invite code table row
  │
  ├─ No confirmation dialog for active unused codes? NO — show inline confirm.
  │    Confirmation: replace "Delete" button with "Confirm delete?" text + [Yes] [No] buttons inline
  │    (avoids modal overhead, stays in-table)
  │
  ├─ Admin clicks [Yes]
  │    → DELETE /api/admin/invite-codes/:id
  │    ├─ 200 OK → toast "Invite code deleted" → row removed from table
  │    └─ error → toast error "Something went wrong. Please try again."
  │
  └─ Admin clicks [No] → restore "Delete" button (cancel confirmation)
```

Note: Only unused codes can be deleted. Used/expired codes are shown read-only — Delete button is absent or disabled for them.

### Admin: Change User Role

```
Users table row: Role column shows current role as a <select> or dropdown
Admin changes the select value
  │
  ├─ Change is not immediate — an "Update" button appears in the Actions column
  │    (or the select triggers a confirm dialog — use inline approach for consistency)
  │
  └─ Admin confirms
       → PATCH /api/admin/users/:id { role: 'ADMIN' | 'USER' }
       ├─ 200 OK → toast "Role updated" → table row refreshes
       └─ error → toast error "Something went wrong. Please try again."
```

Implementation note: Use a native `<select>` styled via shadcn `<Select>` component. If shadcn Select is not in the Phase 1 component set, use a simple `<select>` with Tailwind styling — do not add Select to the shadcn install list without updating D-15.

Alternative (simpler): Two buttons per user — "Make Admin" / "Make User" visible based on current role. Simpler, no extra component. **Use this approach.** Avoids needing shadcn Select in Phase 1.

### Admin: Deactivate User

```
Admin clicks "Deactivate" button in users table row
  │
  ├─ Inline confirmation (same pattern as delete invite code):
  │    Replace button with "Deactivate account?" + [Yes] [No]
  │
  ├─ Admin clicks [Yes]
  │    → PATCH /api/admin/users/:id { isActive: false }
  │    ├─ 200 OK → toast "Account deactivated" → row updates Status badge to "Inactive"
  │    └─ error → toast error "Something went wrong. Please try again."
  │
  └─ Admin cannot deactivate their own account (button absent for own row)
```

### Route Guards

```
Unauthenticated user visits any protected route (/dashboard, /admin, etc.)
  → Redirect to /login (replace history entry)
  → No toast, no error — clean redirect

Authenticated non-admin user visits /admin
  → Redirect to /dashboard
  → Toast warning: "Access denied."

Authenticated user visits /login or /register
  → Redirect to /dashboard

App mount (AuthProvider):
  → Call GET /api/auth/me
  → 200: set user in context, render routes normally
  → 401: clear user in context, any protected route redirects to /login
  → Show nothing (null) during initial auth check to prevent flash
```

## Accessibility Contract

### Keyboard Navigation

- All interactive elements reachable by Tab key in logical DOM order
- Auth form tab order: Username → Password → (Invite code on register) → Submit button → Secondary link
- Sidebar tab order: nav items top-to-bottom → Log out button
- Admin table: Delete/action buttons in each row are Tab-reachable; inline confirmation replaces the button in place (no focus trap needed)
- Enter key submits the focused form (native HTML form behavior)
- Escape key cancels inline confirmations in admin table (restore original button)

### ARIA Labels

| Element | ARIA |
|---------|------|
| Login page h1 | `<h1 className="sr-only">Sign in</h1>` (card title is visual heading, not h1) |
| Register page h1 | `<h1 className="sr-only">Create account</h1>` |
| Password input | `aria-label="Password"` (Label component handles this via `htmlFor`) |
| Submit button (loading) | `aria-busy="true"` when in loading state |
| Sidebar nav | `<nav aria-label="Main navigation">` |
| Active nav item | `aria-current="page"` on the active `<a>` |
| Admin page nav skip | Not required in Phase 1 (sidebar is not long enough to merit skip links) |
| Invite codes table | `<table aria-label="Invite codes">` |
| Users table | `<table aria-label="Users">` |
| Inline confirmation | `role="alert"` on the confirmation text so screen readers announce it |
| Toast (Sonner) | Sonner uses `role="status"` by default — no override needed |
| Loading spinner | `aria-hidden="true"` on the `<Loader2>` SVG; rely on button's `aria-busy` |

### Focus States

- Do not remove `outline` CSS property — shadcn/ui's default focus ring uses `ring-2 ring-ring` which is visible and accessible
- Focus ring color token: `--ring` (defaults to neutral-950 in light, neutral-300 in dark)
- All interactive elements must show a visible focus indicator when focused via keyboard

### Screen Reader Hints

- Form field errors (`<FormMessage>`) are announced via `aria-live="polite"` — this is built into shadcn Form; no extra work needed
- Toast notifications (Sonner) are announced automatically via `role="status"` / `aria-live`
- Status badges in tables (Active/Used/Expired, Admin/User) must convey meaning by text, not color alone — text is present, color is supplementary

### Color Contrast

All text must meet WCAG AA (4.5:1 for body text, 3:1 for large text/icons):
- shadcn/ui neutral theme is designed to pass WCAG AA out of the box
- Muted foreground (`--muted-foreground`) on muted background (`--muted`) must be verified — neutral theme meets this
- Destructive text (`text-destructive`) on white (`--background`) must meet 4.5:1 — red-500 on white is approximately 4.6:1, passes AA
